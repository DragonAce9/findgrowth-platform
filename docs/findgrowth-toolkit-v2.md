# Инструментарий FindGrowth v2: честная статистика + кастомный ML

Редакция 2 (октябрь 2026). Заменяет первую редакцию v2, которая существовала только как сообщение в чате. Первая редакция сохранена по содержанию везде, где она не противоречит решениям, принятым после неё: ручной канал holdout через Поручение, разделение «от первого визита» на две задачи, работа только на синтетике до файла пилота.

Правила этого документа:

- У каждого инструмента стоит статус: **в коде** (есть функция и тест, указан файл), **запланировано** (решение принято, кода нет), **ждёт DOR** (нельзя начинать, пока не выполнено внешнее условие из раздела 8).
- Все числовые результаты моделей в документе получены на синтетических данных и помечены как синтетические. Реальных данных у проекта нет. Числа вида «91 %» или «24 %» как результат продукта не используются. Формула SaaS LTV = ARPU ÷ churn не используется; LTV в продукте — наблюдаемая выручка по горизонту внутри `unitEconomics` (`src/engine/unit-econ.ts`). Функция `cohortHorizons` этот расчёт делает, но наружу не экспортируется.
- Слово «эффект» применимо только к измеренной разности между treatment и control при подтверждённом holdout (раздел 5.4). Всё остальное — «наблюдаемая разница» или «прогноз».

## 1. Введение: три кита и слой, к которому относится каждый инструмент

Позиционирование платформы стоит на трёх утверждениях. Каждый инструмент в документе принадлежит одному из них.

| Кит | Утверждение | Слой | Раздел |
|---|---|---|---|
| 1. Прогноз от первого визита до повторной покупки | Регуляризованный ML ранжирует людей: кто готов к первой покупке, кто в зоне риска после первой. Выход модели — порядок, не число на экране. | Скоринг | 4 |
| 2. Математическая честность фактов | Интервалы Уилсона, Каплан–Мейер с цензурированием, lift с интервалом вместо косинуса, явный baseline для любой модели. Никаких точечных долей на сотнях заказов. | Факты | 3 |
| 3. Закон контролируемого Measured Lift | Вёдра по приоритету, внутри каждого автоматический 50/50 holdout. Результат кампании — разность с контролем и интервал. Если эффекта нет, экран говорит «эффекта нет». | Измерение | 5 |

Связь между китами — одно правило, унаследованное из первой редакции: **прогноз ранжирует, holdout измеряет, на экране — только измеренное**. `predicted_lift` на экране запрещён; `measured_lift` появляется только из `measureLift` (`src/engine/holdout.ts`). ML живёт внутри этой пары: он выбирает, кому писать первым, и никогда не измеряет сам себя.

## 2. Архитектурные принципы (без изменений по сути)

**Данные приходят батчами файлов, не потоком.** Срез (`cuts`) — это файл заказов, файл событий и NPS на дату `asOf`. Нет real-time на принятие решения в сессии; любой скоринг — на дату среза. Отсюда первая цель — propensity повторной покупки, под которую уже есть данные, снапшот и экран.

**Чем является выход модели.** Порядком, не вероятностью. CEO не видит «0,63»; он видит ведро и факт из слоя статистики по этому ведру (наблюдаемая доля повтора с интервалом). Карточки проблем на экране не содержат цифр в прозе — это закреплено голден-тестом (`src/engine/golden.test.ts`: `assert.doesNotMatch(card.problem, /\d/)`).

**Point-in-time корректность.** Каждый признак считается на дату прогноза (для цели 1 — на `T1`, дату первой покупки), не на `asOf`. `featuresFor` (`src/engine/features.ts`) фильтрует события и заказы по `timestamp <= T1`; тест `features use only events at or before the first purchase` (`src/engine/v2.test.ts`).

**Семплирование.** При `sampleEvery > 1` в конфиге среза сессионные счётчики масштабируются (`pipeline.ts`, вес `weight`) или исключаются из признаков. Сессионные признаки velocity / intent ratio / cart friction на семплированных событиях не считаются.

**Идентичность.** `stable_id` — хеш колонки визита (`stableIdColumn`); `assertStableIdColumn` отвергает `email` и `customer_id` как колонку визита (голден-тест `stable_id rejects email and customer_id`). Email, телефон и `customer_id` попадают в граф идентичности только как HMAC-узлы (`identity.ts`, `hash.ts`, `piiHmac`). В признаки они не входят.

### 3.2 Принципы, которые эти инструменты закрепляют

- Доля без интервала на экран не выходит.
- Отсутствие данных не заменяется нулём: сезонная поправка, цикл, карточка модели — все возвращают «недоступно» текстом без цифр.
- Любой скоринг сравнивается с явным baseline, который записан в карточке модели (раздел 4.1.4).
- Бинарная метка «купил повторно за `windowDays`» применяется только к зрелым; остальные — цензурированные наблюдения в KM. `windowDays` (120 в демо-конфигах) — окно платформы, не цикл пополнения; цикл берётся из KM.

## 4. Кит 1. Прогноз: слой скоринга

### 4.1 Цель 1: propensity повторной покупки

Целевая переменная: \( P(T_2 - T_1 \le w \mid \text{первый заказ, поведение до него, канал}) \). Это карман risk / lost из диагностики (`queryDiagnostic`), только ранжированный.

#### 4.1.1 Лестница моделей

Каждая следующая модель обязана побить предыдущую на отложенных по времени когортах с интервалом разрыва, не пересекающим ноль. Не побила — в прод идёт предыдущая.

| Ступень | Модель | Файл | Статус |
|---|---|---|---|
| 0 | Правило RFM: терцили recency / frequency / monetary по train + доля повтора роли первого SKU (`0,85 · ячейка + 0,15 · роль`, лапласово сглаживание) | `ml/findgrowth_ml/propensity.py` `rfm_scores`; упрощённый вариант «orders ≥ 2» в `train.py` `rfm_score` | в коде |
| 0′ | Beta-Geometric: BG/NBD через `lifetimes`, если импортируется; иначе замкнутая форма с моментами по train. Второй baseline по Brier | `propensity.py` `beta_geometric_scores` | в коде (замкнутая форма; `lifetimes` в `requirements.txt` нет) |
| 1 | Логистика с elastic net (`l1_ratio = 0,5`, `C = 1`, `saga`), стандартизация по train | `propensity.py` `elastic_net_proba`; `train.py` `fit_scores` | в коде |
| 2 | Cox с elastic net или GBM с objective Cox/AFT — survival-постановка, стыкуется с KM | — | запланировано (`lifelines` в `requirements.txt`, Cox не обучается; `card.cox = null`) |
| 3 | GBM `max_depth 3`, монотонные ограничения (больше заказов → не ниже скор), большой `min_child_samples` | гейт `src/engine/scoring-gate.ts` `assertGbmAllowed`, `train.py` `refuse_gbm` | гейт в коде; модель запланирована, включается при ≥ 500 позитивов |
| 4 | Пулинг между брендами: общий слой категории + бренд-поправка; только проекты с `poolingConsent` | `propensity.py` `pooled_rows`, `category_versus_brand`; `platform-db.ts` `poolingProjectIds`; миграция `0004_models_pooling.sql` | механика в коде; выигрыш пула не показан (4.1.5) |
| 5 | Uplift: T-/X-learner, causal forest на накопленных holdout-данных; оценка — Qini против propensity-ранжира | `propensity.py` `t_learner_uplift`, `qini_curve`, `qini_area` | механика в коде; ждёт DOR (нет реальных holdout-исходов) |

**Правило EPV.** При ~100 положительных исходов регуляризованная логистика держит 5–10 признаков. Это ограничение, а не глубина деревьев. Ниже 100 позитивов — модель не включается даже в shadow (раздел 6.2).

#### 4.1.2 Признаки

`FeatureRow` (`src/engine/features.ts`) на дату `T1`: `visits_before_t1`, `pdp_depth`, `days_first_seen_to_t1`, `basket_roles` (состав первой корзины по ролям SKU), `revenue`, `discount`, `channel` (first-touch), `device`, `nps` (последний ответ до `T1`). Сохраняется в `cuts.features_json` (миграция `0003_features.sql`). Статус: в коде.

Запланировано к добавлению: количество позиций первой корзины, день недели, возвраты в корзину, дней с первой покупки относительно наблюдаемого цикла (от KM).

Жёсткие правила:

- Признак с информацией после `T1` даёт высокий PR-AUC на валидации и ничего в проде. Проверка на копию метки — `features_without_leakage` (`propensity.py`); карточка модели падает, если копия метки не отловлена.
- `email`, `name`, телефон в признаки не входят. Признаки, коррелирующие с защищёнными характеристиками, исключаются при аудите.
- При `sampleEvery > 1` сессионные счётчики масштабируются или исключаются.

### 5.2 Поручение как единственный канал holdout

Платформа ничего не отправляет и не выгружает адреса. Исключение control — ручной шаг бренда. Чтобы ручной канал был проверяемым, Поручение (`klaviyoSteps`, страница «Поручение» в `docs/tz-semantika.md`) содержит четыре части:

| Часть | Содержание | Сейчас в коде | Статус |
|---|---|---|---|
| ЧТО | Сегмент, предложение (пара из `topCoPurchases`), окно отправки из пика хазарда KM: не «через 60 дней», а «день 38–52 с момента покупки, где у этой категории пик повторов». Источник — `hazardPeak` и квартили `observedCycle` | `when` = «`cycleDays` дн. после Placed Order» | запланировано: заменить `when` на окно вокруг `hazardPeak` |
| КОМУ | Список treatment по ключу бренда | Условие сегмента Klaviyo («Placed Order = 1, старше N дн.»), списка нет | запланировано |
| КОМУ НЕ | Явный список control по тому же ключу. «Эти — да, вот эти — нет» защищает от сегмента, который в Klaviyo соберётся шире | — | запланировано |
| КАК ПОДТВЕРДИТЬ | Какой столбец бренд загружает в следующем срезе: события отправки/открытия с тем же ключом или выгрузку получателей кампании. Один столбец, не интеграция | — | запланировано |

**Ключ бренда.** Это его собственные поля из его же файла: `customer_id` или номер последнего заказа. Не наш хеш: `user:hmac1:…` бренд обратно не развернёт. Мы возвращаем бренду его ключи, а не выгружаем адреса; запрет «адреса не покидают платформу» это не трогает. Если в файле нет ключа бренда — Поручение остаётся «что и как» без «кому» и говорит об этом прямо.

**Правило arm остаётся нашим** (`sha256(entity | snapshot | salt)`, 50/50). Бренд его не воспроизводит — он получает два списка.

**Что это добавляет в движок** (всё — запланировано):

- Таблица соответствия `stable_id → ключ бренда` внутри проекта. Сейчас ключ хешируется и теряется. Это псевдонимизированные данные бренда у процессора — одна строка в DPA. Инвариант «email / customer_id не могут быть `stable_id`» сохраняется: ключ бренда — отдельный столбец соответствия, не идентификатор визита.
- Поле «статус holdout» у снимка: подтверждён / не проверен / нарушен, с долей контаминации и способом проверки.
- Парсер подтверждения: столбец «получил письмо» по ключу бренда в следующем срезе → доля соблюдения по arm.
- Формулировки лифта по трём состояниям с голден-тестом (5.4).

### 5.3 Анализ по назначению (intent-to-treat)

Сравниваем arm по снимку, а не по факту отправки.

- **Случайная контаминация** (забыли, сегмент собрался шире): эффект размывается к нулю. ITT консервативен — ручной канал не может надуть лифт, только занизить. При доле control с письмом \( p_c \) ITT занижен в \( (1 - p_c) \) раз. При известной доле соблюдения \( c \) показываем \( \text{ITT}/c \) вторым числом с пометкой «оценка на получивших».
- **Селективное отклонение** («этим тоже отправлю, они хорошие»): ломает рандомизацию, ITT не спасает. Единственная защита — зафиксировать ответ бренда при загрузке подтверждения: «отклонения от списка были случайными или по выбору».

Статус: запланировано.

### 5.4 Три состояния лифта на экране

| Состояние | Условие | Что пишем | Интервал |
|---|---|---|---|
| 1. Холдаут подтверждён | Есть данные об отправке; контаминация \( p_c \le 20\,\% \); отклонения случайные | «Измеренный эффект» | Ньюкомб (+ ITT/c вторым числом при известном c) |
| 2. Холдаут не проверен | Отправка была, данных об отправке нет | «Наблюдаемая разница между группами», без слова «эффект» | Тот же интервал, другая формулировка |
| 3. Холдаут нарушен | \( p_c > 20\,\% \) или отклонение селективное | Лифт не называем; показываем, что группы разошлись, и предлагаем новый снимок | Не показывается как результат |

Порог 20 % не выдуман: при \( p_c = 0{,}2 \) ITT уже занижен на пятую часть, и интервал бесполезен для решения. Голден-тест: слово «эффект» появляется только в состоянии 1. Статус: запланировано.

### 5.5 Калькулятор мощности в Поручении

См. 3.3. В блоке «Приёмка задачи» — «в control N человек; чтобы увидеть X п.п. при наблюдаемой доле повтора, нужно M». Если `N < M` — Поручение говорит, что этот срез даст только накопление в байесовский приор (3.3), не решение. Статус: запланировано.

## 8. Открытые решения / DOR

| Решение | Что нужно, чтобы начать | Что блокирует |
|---|---|---|
| Правило arm, воспроизводимое в Klaviyo | Доступ к сегмент-билдеру Klaviyo пилота; `customer_id` как свойство профиля; час на проверку | Автоматическое исключение control (5.6) |
| Onsite-коннектор + cookie-consent | Решение ставить сниппет на сайт пилота; текст consent; контракт событий (4.3) | Цель 2b целиком; хранение `anonymous_id` между сессиями |
| Файл пилота | Чеклист 6.3 | Любая модель на реальных данных; цель 2a; проверка контаминации |
| Пулинг между брендами | ≥ 2 бренда с `poolingConsent`, у каждого < 300 позитивов, в пуле ≥ 1 000; пул должен выиграть у модели бренда (на синтетике не выиграл) | Ступень 4 |
| Uplift | Накопленные holdout-исходы с реальным treatment / control, где эффект больше шума (на синтетике T-learner проиграл propensity) | Ступень 5 |
| Пересмотр DPA | Строка о таблице `stable_id → ключ бренда`; отдельно — если когда-нибудь выбирается путь «выгрузка ID» | Поручение с «кому» (5.2) |

**Не делать** (вне зависимости от DOR): коннекторы на отправку, фактическую отправку писем, `predicted_lift` на экране, экспорт адресов, OAuth-интеграции, мониторинг 24/7.

## 9. Порядок внедрения

1. Слой фактов (раздел 3.1) — в коде.
2. Point-in-time признаки, baseline RFM и Beta-Geometric, elastic-net с метриками на временном сплите, карточка модели, shadow, champion/challenger, PSI, kill-switch — в коде на синтетике.
3. Поручение как канал holdout: таблица соответствия, два списка по ключу бренда, окно из `hazardPeak`, статус holdout, парсер подтверждения, три состояния лифта с голден-тестом, калькулятор мощности — делается без пилота на демо и синтетике.
4. Честная статистика для сегментов: усадка, Benjamini–Hochberg, байесовское накопление между срезами, единое состояние «мало данных», reason codes — на синтетике.
5. Гейт EPV на ведро и чеклист файла пилота на странице «Входы».
6. Цель 2a: `FeatureRow` непокупателя, вторая целевая переменная, baseline «брошенная корзина» — спецификация и синтетика сейчас, данные — после пилота.
7. Цель 2b: контракт сниппета и co-view lift на `rees46` — сейчас; Thompson sampling и onsite-holdout — после коннектора и consent.
8. Cox / GBM с ограничениями / пулинг — по мере выполнения гейтов на позитивы.
9. Uplift — на накопленных holdout-данных.
